## 1. 背景与问题陈述

### 1.1 结论摘要

将企业 AI 领域 Ontology（本体论）方法论与 PromiseLink 解析流程对比后得出：

**PromiseLink 的解析流程本质上是一个「自底向上生长出来的窄域 Ontology」——六步中五步已有对应物，唯一缺的是把隐式结构显式化。**

| Ontology 六步 | PromiseLink 现状 | 成熟度 |
|---|---|---|
| ① 定义概念（Class） | `Event` / `Entity` / `Todo` / Promise + `RelationshipBrief`（刻意收敛 4 类核心实体） | ✅ |
| ② 定义属性 | SQLAlchemy 模型字段 + Pydantic schema | ✅ |
| ③ 定义关系 | `Association` 关联 + 4 类详情页互相跳转（关系网的 UI 化） | ✅ |
| ④ 声明实例 | 每次录入流式解析出的真实记录（增量而非批量） | ✅ |
| ⑤ 定义约束 | InputScope 8 类枚举、状态机；多候选人脉强制用户确认 | ⚠️ 软约束+人工兜底 |
| ⑥ 定义推理规则 | Step04 Todo 生成 / Step05 Promise 双向分析 / Step11 关联发现 | ⚠️ 推理在 LLM 内部，非显式层 |

### 1.2 三个本质差异

1. **先验建图 vs 后验演化**（最大差异）：企业 Ontology 自顶向下先定地图再灌数据；PromiseLink 自底向上，schema 从真实录入语料演化（InputScope 扩到 8 类、Promise 双向分析均是被真实用例推动）。对个人 CRM 这是优势——概念空间小且以「人」为中心，先验建图反而过度设计。
2. **显式推理引擎 vs LLM 隐式推理**：Ontology 靠规则引擎（确定性可解释）；PromiseLink 把推理塞进 LLM，换灵活性、付确定性，用三贤者投票 + 用户纠偏兜底。
3. **约束执行位置**：Ontology 在知识库层 fail-closed；PromiseLink 软化为 human-in-the-loop——在人际数据域是正确决策（「张三」是谁本来就有歧义）。

### 1.3 核心问题

当前 4 类实体 + 属性 + 关系 + 约束全部**隐式**分散在三处：
- Pydantic / SQLAlchemy schema（代码）
- LLM 解析 prompt（字符串）
- 开发者脑中（无文档）

后果：换 LLM 时（Moka→DeepSeek 已发生一次）解析输出结构靠人肉比对；prompt 迭代无回归基准；纠偏信号（用户每次选择正确人脉）被丢弃。

## 3. 五个工作流

### W1 — 《解析语义契约》显式化（P0，S 级，~2 天）

**目标**：把隐式 Ontology 变成看得见、可维护、可版本化的单一事实源。

**关键架构决策（七角色共识）**：**代码驱动，文档生成**——Pydantic schema 为权威源（single source of truth），契约文档由脚本从 schema 自动生成骨架 + 人工维护「语义说明」段落。
理由：TD-044 的教训（pyproject/Dockerfile/ci.yml 三份手写依赖清单漏了 pyotp）证明**双份手写必漂移**。契约文档若手写为权威，必然与代码 schema 漂移；反过来从 schema 生成则天然一致。

**交付物**：
- `scripts/generate_semantic_contract.py`：从 4 类实体的 Pydantic schema 生成 Markdown 契约骨架（概念/属性/关系/约束/枚举五节）
- `docs/spec/PARSING_SEMANTIC_CONTRACT.md`：契约文档 v1.0.0（骨架生成 + 语义说明人工补全：每字段业务含义、必填性理由、歧义处理策略）
- 解析 prompt 头部注释标注契约版本号

**验收标准**：
1. 契约文档由 CI 生成比对，人工改动 schema 生成段 → CI 失败（防漂移）
2. 契约版本号与 CHANGELOG 联动（schema 变更 = MINOR/PATCH bump）

### W2 — 解析黄金基准集（P0，S 级，~2 天，依赖 W1）

**目标**：给「换模型/改 prompt」装上回归仪表——Ontology 方法论中「规则体系」的可测试形态。

**交付物**：
- `tests/golden/` 黄金集：≥30 条用例，三类分层：
  - `must_extract`：明确应抽出的人脉/待办/承诺（如「答应下周三给方案」→ Promise + Todo，双方+截止时间）
  - `must_not`：不应产生结构的闲聊（防过度抽取）
  - `ambiguous`：多候选人脉/时间歧义，断言「进入纠偏流程」而非断言唯一答案
- 基准跑器：pytest 参数化，LLM 输出 vs 黄金标注的结构化 diff（字段级），输出通过率报告
- 数据来源：合成数据为主（**不得含真实用户 PII 入 git**，见 §5）

**验收标准**：换 DeepSeek 版本 / 改 prompt 后跑基准，通过率不降（≥ 基线）才允许合入。

### W3 — 纠偏回流机制（P1，M 级，~1 周，依赖 W1）

**目标**：把用户纠偏从「一次性 UI 交互」升级为「ontology 自演化数据流」——后验派 Ontology 独有优势，当前被浪费。

**交付物**：
- `EntityCorrection` 记录：用户在多候选人脉/分区展示时的每次纠偏（原文片段、候选集、用户选择、时间戳）
- 聚合视图：按「错误模式」聚类（同名不同人 / 职位歧义 / 时间格式），月度人工审核 → 更新契约「歧义处理策略」节或 prompt few-shot
- **隐私**：纠偏记录全程过 PII Redactor，聚合视图仅存模式统计不存原文

### W4 — 关联推理轻量规则（P1，M 级，~2 周，= ROADMAP B4 实施细化）

**目标**：补上 Ontology 第⑥步的确定性部分——能用 SQL/规则算的绝不进 LLM。

**交付物**：
- 同义词字典 + difflib 80% cutoff 实体规范化（B4 原案，用户确认机制复用 W3 回流）
- SQL 共现规则：两人脉 ≥N 次同事件出现 → 「高频联系人」标签 → RelationshipBrief 强化
- 明确边界：只做「共现/频率/别名」三类确定性规则；语义推断（「A 是 B 的领导」）留给 LLM + 用户确认

### W5 — 跨语言实体关联（P2，远期，= ROADMAP L4/L5，依赖 W1+W4）

**目标**：同一主体跨语言归一（"John Smith"="约翰·史密斯"）。依赖契约（W1）与规范化（W4）先行。技术路线按 ROADMAP v0.9.5 既有结论（LLM 语义相似度 + 人工确认，不引入实时翻译 API）。

## 5. 安全区与红线

1. 黄金集/测试夹具：**仅合成数据**入 git（真实姓名/公司/手机号一律伪造）
2. 纠偏回流：原文过 PII Redactor 后才落库；聚合层仅模式统计
3. 契约文档：不含任何真实用户数据示例
4. CI：黄金基准 job 不自动跑 PR（LLM 成本），workflow_dispatch + 定期触发

## 6. 不做清单（继承既有决策，再次确认）

- ❌ 迁移图数据库（Neo4j/FalkorDB/Kuzu）——破坏「本地运行、无 Docker」
- ❌ RDF/OWL 本体语言与推理机——过重，4 类实体规模下 SQL 足够
- ❌ 向量存储/embedding 基础设施（除非 L4 调研结论要求）
- ❌ 契约文档手写为权威源（防 TD-044 式三处漂移重演）
- ❌ 自动合并实体（一切规范化合并必须用户确认）
