# 2026-07-29 WSS 中继 BUG 测试覆盖不足 + 微信小程序登录失败 根因分析

> DevSquad V4.4.0 7-Role 共识分析
> 日期：2026-07-29
> 触发：用户报告"配对成功但 WSS 中继连接未建立"BUG + 微信小程序登录失败
> 方法：DevSquad 7-Role 并行评估 + 共识汇总

## 一、事件摘要

| 事件 | 严重度 | 影响范围 | 发现方式 |
|------|--------|----------|----------|
| 配对成功但 WSS 中继未建立 | P0 | 小程序无法访问本地数据，核心功能不可用 | 人工测试 |
| 微信小程序登录失败 | P0 | 用户无法登录小程序，完全不可用 | 人工测试 |

**核心问题**：两个 P0 级 BUG 均未在测试阶段发现，直到用户人工测试才暴露。

## 二、DevSquad 7-Role 并行分析

### 角色 1：架构师（Architect）

**视角**：架构设计层面的缺陷

**发现**：
1. **WSS 生命周期设计与测试设计脱节**
   - `pair/activate` 接口在设计中应"激活并启动 WSS"，但实现只写了 .env，依赖 lifespan startup 事件启动 WSS
   - 架构上缺少"激活后状态校验"环节——激活成功 ≠ 服务可用
   - 这违反了"命令-查询职责分离"原则：activate 是命令，但没有查询验证服务是否真的启动

2. **微信登录调用链跨 3 个独立服务**
   - 小程序前端 → 网关 → 微信 API，跨 3 个独立服务
   - 每个服务独立测试都通过，但集成点无人验证
   - 架构上缺少"跨服务集成契约测试"

**建议**：
- 引入"激活后健康检查"机制：activate 接口返回后，客户端应轮询 WSS 连接状态
- 建立跨服务契约测试（Consumer-Driven Contract Testing）

### 角色 2：产品经理（PM）

**视角**：需求定义与验收标准

**发现**：
1. **验收标准缺失"端到端可用性"**
   - PRD 定义了"配对成功"和"WSS 连接建立"两个功能点，但验收标准只写了"配对接口返回 200"
   - 没有定义"用户场景级验收标准"：用户配对后能否立即在小程序访问本地数据

2. **用户旅程未映射到测试用例**
   - 用户旅程：扫码 → 配对 → 激活 → 打开小程序 → 看到本地数据
   - 测试用例只覆盖前 3 步，后 2 步缺失

**建议**：
- 每个核心用户旅程必须有对应的 e2e 测试
- 验收标准必须包含"端到端可用性"而非仅"接口返回正确"

### 角色 3：安全专家（Security）

**视角**：安全影响

**发现**：
1. **WSS 未建立导致的安全风险**
   - 如果 WSS 未建立，小程序可能尝试直连本地基础版（之前的 BUG）
   - 这会暴露本地服务到公网，违反"数据从不出家门"原则

2. **微信登录失败的账号安全**
   - 登录失败可能导致用户使用 PoC 后门（poc_anonymous_access）
   - 需确认 PoC 后门在生产环境已关闭

**建议**：
- WSS 连接状态应作为安全门禁：未连接时小程序应禁用所有功能
- 登录失败时不应降级到不安全的认证方式

### 角色 4：测试专家（Tester）—— 核心责任方

**视角**：测试策略与覆盖度

**发现**（根因分析）：
1. **测试维度严重不完整**（违反 DevSquad Iron Rule 3）
   - 只测 Happy Path：`test_pair_mode.py` 只验证 activate 接口返回 200 和 .env 写入
   - 缺失 Integration 维度：没有验证 activate 后 WSS 客户端是否真正启动
   - 缺失 E2E 维度：没有"配对→激活→小程序访问本地数据"的完整链路测试

2. **测试断言过弱**（违反 DevSquad Iron Rule 2）
   - 断言只检查 `response.status_code == 200` 和 `success is True`
   - 没有检查副作用：`app.state.relay_wss_client` 是否被设置
   - 没有检查实际状态：WSS 客户端是否 `connected == True`

3. **测试未覆盖错误场景**
   - 没有测试"activate 成功但 WSS 启动失败"的场景
   - 没有测试"settings 缓存未刷新导致 WSS 未启动"的场景

4. **根本原因：测试设计没有从"用户价值"出发**
   - 测试目标应该是"用户配对后能使用小程序访问本地数据"
   - 实际测试目标是"activate 接口返回 200"
   - 这是典型的"测试了代码而非测试了行为"

**建议**（改进措施）：
- 强制执行 DevSquad Iron Rule 3：每个模块测试必须覆盖 7 维度
- 引入"用户旅程 e2e 测试"作为发布门禁
- 测试断言必须包含副作用验证，不能只检查返回值
- 建立"测试用例评审"机制：测试用例必须由非开发人员评审

### 角色 5：开发工程师（Coder）

**视角**：代码实现

**发现**：
1. **`pair/activate` 实现与文档不一致**
   - 文档说"writes to .env, starts WSS relay"
   - 实现只写 .env，返回"即将启动中继服务"但实际不启动
   - 这是"文档先行但代码未跟进"的典型案例

2. **settings 缓存陷阱**
   - `get_settings()` 使用 `@lru_cache`，写入 .env 后不刷新缓存
   - 导致 `fresh_settings.pro_license_key` 仍为空，WSS 启动条件不满足
   - 修复：调用 `get_settings.cache_clear()` 后重新获取

**建议**：
- 代码实现必须与文档同步更新（活文档原则）
- `@lru_cache` 的配置类必须有显式缓存刷新机制

### 角色 6：DevOps 工程师

**视角**：部署与配置

**发现**：
1. **微信小程序后台域名配置遗漏**
   - `prod.ts` 注释明确提到"需在微信 MP 后台添加 https://gateway.promiselink.cn 到 request 合法域名"
   - 但这一配置项没有纳入部署检查清单
   - `project.config.json` 中 `urlCheck: true` 会在开发者工具中检查，但生产环境不检查

2. **开发环境配置冲突**
   - `dev.ts` 中 `TARO_APP_PRO_API_URL = 'http://192.168.1.103:8001'`
   - 微信小程序不允许 http 请求（必须 https）
   - 开发者工具需要关闭"域名校验"才能用 http，但生产环境无法关闭

**建议**：
- 部署检查清单必须包含"微信小程序后台合法域名配置"
- dev 环境应使用 ngrok 或 localhost https 代理，而非裸 http IP

### 角色 7：UI 设计师

**视角**：用户体验

**发现**：
1. **错误反馈不友好**
   - "配对成功但 WSS 未建立"时，用户看到的是"专业版激活成功"
   - 实际功能不可用，但 UI 没有任何提示
   - 用户点击人脉才看到"local basic-edition is not connected"，错误信息技术化

2. **登录失败无重试引导**
   - 微信登录失败只显示"微信登录失败"，没有告诉用户原因
   - 没有提供"检查网络"/"检查域名配置"等引导

**建议**：
- 激活后应显示 WSS 连接状态（连接中/已连接/失败）
- 错误信息应用户友好化，提供可操作的解决建议

## 三、5-Why 根因分析

### BUG 1：配对成功但 WSS 中继未建立

```
Why 1: 为什么 WSS 未建立？
  → pair/activate 接口只写了 .env，没有启动 WSS 客户端。

Why 2: 为什么测试没发现？
  → 测试只验证了接口返回 200 和 .env 写入，没有验证 WSS 客户端启动。

Why 3: 为什么测试没验证 WSS 客户端启动？
  → 测试用例从"接口契约"设计，没有从"用户旅程"设计。

Why 4: 为什么没有从用户旅程设计测试？
  → 缺少 e2e 测试策略，测试计划只覆盖单元测试和接口测试。

Why 5: 为什么缺少 e2e 测试策略？
  → 项目未强制执行"发布前必须做模拟真实用户使用的 e2e 测试"这一规则。
     (用户规则 3 已明确要求，但未落地到测试计划)
```

**根因**：测试策略缺失 e2e 维度，违反用户规则 3。

### BUG 2：微信小程序登录失败

**2026-07-29 更新**：用户反馈微信后台合法域名早就配置好了，之前测试能通过。经深入排查，真正根因如下。

```
Why 1: 为什么登录失败？
  → 微信登录请求走 http://localhost:8001/api/v1/auth/wechat/login（非 https + localhost 不可达）。

Why 2: 为什么走 localhost:8001？
  → dist 编译产物中 GATEWAY_URL = "http://localhost:8001"（grep dist/common.js 确认）。

Why 3: 为什么 dist 中是 localhost:8001？
  → .env.development 文件中 TARO_APP_PRO_API_URL=http://localhost:8001，
     Taro 编译时 process.env.TARO_APP_PRO_API_URL 优先于 config/dev.ts 的值，
     覆盖了 dev.ts 中的 http://192.168.1.103:8001。

Why 4: 为什么 .env.development 中是 localhost:8001？
  → 这是早期开发遗留配置，后续切换到网关架构后未同步更新 .env.development。

Why 5: 为什么没有发现配置过期？
  → 测试时可能用 .env.production 编译（配置正确），或开发者工具关闭了域名校验，
     未发现 .env.development 的配置在 dev 模式编译下会导致微信登录失败。
```

**根因**：`.env.development` 配置过期（localhost:8001），dev 模式编译后 GATEWAY_URL 为非 https 的 localhost 地址，微信小程序无法访问。

**修复**：
1. 修改 `.env.development` 中 `TARO_APP_PRO_API_URL` 为 `https://gateway.promiselink.cn`
2. 修改 `.env.development` 中 `TARO_APP_API_URL` 为 `https://gateway.promiselink.cn/api/v1`
3. 重新编译 `npm run build:weapp`
4. 验证 dist 中无 localhost，GATEWAY_URL = "https://gateway.promiselink.cn" ✅

### 教训提炼

1. **测试必须覆盖用户旅程，不能只覆盖接口契约**
   - "接口返回 200" ≠ "功能可用"
   - 必须从"用户能否完成业务流程"设计测试

2. **发布前必须执行 e2e 测试**（用户规则 3）
   - 模拟真实用户操作：扫码 → 配对 → 激活 → 小程序访问数据
   - e2e 测试应作为发布门禁，不通过不允许发布

3. **部署检查清单必须包含所有平台侧配置**
   - 服务器配置 + 微信小程序后台 + DNS + SSL 证书
   - 清单更新必须跟随架构演进

4. **测试断言必须验证副作用，不能只检查返回值**
   - activate 接口必须验证 `app.state.relay_wss_client is not None`
   - WSS 客户端必须验证 `connected is True`

5. **文档与代码必须同步**（活文档原则）
   - 文档说"starts WSS relay"，代码必须真的启动
   - 代码变更必须同步更新文档
